## 解決方法

### 1. 必須対応 issue を片付ける

`SEQUENCE` 順ではなく、依存関係の少ないものから順に片付ける。 `auto-resolve` スキルが利用可能なら以下の順番が短工程:

`0050` → `0051` → `0052` → `0059` → `0053` → `0054` → `0060` → `0041` → `0057`

- `0052` ( `parseQueryString` 経路) → `0059` ( OPFS 経路) は同種ガードの片割れなので連続して当てる
- `0053` ( `disabled` の責務修正) → `0054` ( `disabled` + in-flight ガード) は `RequestMediaButton` 系の整合性なので連続して当てる
- `0041` / `0057` は防御 / リークで実装独立、最後にまとめる

### 2. リリース確定作業

すべての必須対応 issue がマージ完了したら、 Git Flow に従い `release/2026.1.0` ブランチを切る。 1 ブランチ・最小コミットで以下をまとめる:

1. `CHANGES.md` の `## develop` セクションを `## 2026.1.0` に変更し、 `**リリース日**: YYYY-MM-DD` を直下に追記する
2. `package.json` の `"version"` を `2026.1.0` に確定する
3. 上記 2 ファイルを 1 コミットで作成する。コミットメッセージは過去のリリースコミット ( 例: `99504205 バージョンを 2025.2.1 に更新し、変更履歴を追加する` ) の形式に揃える

### 3. タグ付け / マージ

`release/2026.1.0` を `main` にマージしてタグ `2026.1.0` を打ち、 `main` から `develop` へ back-merge する ( `git log` 上の `Merge branch 'release/2025.2.0' into develop` と同じ運用)。

### 4. 本 issue のクローズ

5 つの完了条件をチェックリストで再確認し、すべて満たしていれば本 issue を `issues/closed/` へ `git mv` で移動する ( `shiguredo-issues` スキル準拠)。
